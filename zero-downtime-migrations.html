Zero-downtime schema changes: expand, then contract

A deploy is not an instant. For a few minutes, yesterday's code runs against today's schema.

Rename a column in a single migration and you have scheduled an outage. The reason is timing: a deploy rolls out over seconds or minutes, and during that window the old code and the new schema are live at the same time. Every query the old code runs against the renamed column returns an error.

The rule underneath

The schema is never allowed to get ahead of the code still reading it. Any change that breaks that rule — a rename, a NOT NULL added in one step, a type change, a table split — is dangerous. The fix is to turn one breaking change into a sequence of compatible ones.

Five deploys, zero downtime

To rename fullname to full_name:

  • Expand. Add the new column, nullable. Nothing reads it yet; nothing breaks.
  • Double-write. Deploy code that writes both columns, keeping them in sync going forward.
  • Backfill. Copy existing rows in batches, at a pace the database is comfortable with.
  • Switch reads. Deploy code that reads the new column. The old one is now unused.
  • Contract. Stop writing the old column and drop it.

Each step ships alone and rolls back alone. At no point does live code query a column that is not there.

Why it is worth the ceremony

Five small, boring deploys are slower than one clever migration — and that is the point. The clever migration works on your laptop, where there is no gap between old code and new schema. Production always has that gap. Expand-contract is how you make the gap survivable, and the habit generalises: make the new thing exist alongside the old, move the traffic, then remove the old.
