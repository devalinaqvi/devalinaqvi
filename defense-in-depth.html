Defense in depth: securing the VPS and the application

Security isn't one wall. It's layers — and each one assumes the layer above it has already failed.

Security is not a feature you bolt on. It is a set of layers a request passes through on its way in — and so does an attacker. The useful way to think about a server and the app running on it is defense in depth: each layer does its job assuming the layer above it has already failed.

Two problems wearing one word

“Security” covers two jobs that often belong to different people. VPS or infrastructure security is about the box — the network, the firewall, the operating system, the web server. Application security is about the code — who is allowed to do what, and whether input can be trusted. A hardened server running vulnerable code is exploitable; flawless code on an open box is exposed. You need both, and they fail in different ways.

The infrastructure layers

Network edge. Before traffic reaches the box, a proxy like Cloudflare can absorb DDoS, hide the origin IP, and filter the obvious attacks with a WAF.

Firewall. On the host, default-deny inbound and open only the ports you actually serve. The most common real breach is not a clever exploit — it is a database or cache quietly listening on 0.0.0.0 that was never meant to be reachable.

Host and SSH. Keys-only SSH with root login disabled ends password brute force outright. Keep the OS patched, and give every process the least privilege it needs to do its job.

Web server and TLS. Terminate TLS, turn off directory listing, and make sure the server never hands out dotfiles like .git or .env. The site's files should be read-only to the web-server user, so a foothold elsewhere on the box can't rewrite them.

The application layers

Application logic. This is where most real-world compromises actually happen, and where a framework helps but does not save you. Authenticate — who are you. Authorise every action, on every request and not just at login, or you get IDOR. Validate and escape all input, which is what stops SQL injection and XSS. Protect state-changing requests with CSRF tokens.

Data. The thing you are actually protecting. Encrypt sensitive data at rest, keep secrets out of the code and in the environment, and — the part everyone skips — keep backups you have actually restored. A backup you have never tested is a hope, not a plan.

Why layers instead of a wall

Almost no breach is a genius defeating one strong wall. It is a single weak layer — a reused SSH password, an unvalidated form field, a port left open — that the others could not compensate for. Defense in depth means no single mistake is fatal: the firewall covers for the service that shouldn't be exposed, keys-only SSH covers for a leaked password, input validation covers for a bug in the ORM. Build every layer as if the one before it has already failed, because one day it will.
