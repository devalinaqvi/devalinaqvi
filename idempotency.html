Idempotency: the retry is not optional

A client that times out will retry. What that retry does to your database is up to you.

A client that times out will retry. That is not a bug — it is the only sane thing it can do, because the timeout told it nothing about whether the request succeeded. The response might have been lost on the way back.

The failure

Consider a charge endpoint. The card is charged correctly, but the 200 never reaches the client because the connection dropped. The client retries. Without protection, the card is charged a second time, and no error is raised anywhere — both requests did exactly what they were told.

The fix: an idempotency key

The client generates a unique key per logical operation and sends it with the request and every retry:

POST /charge
Idempotency-Key: 9f2c-a17b-...

The server records the key with the result of the first successful call. When a request arrives with a key it has already seen, it does not run the operation again — it replays the stored result. The retry becomes safe: same key, same answer, one charge.

The detail that matters

POST is not idempotent by default. HTTP guarantees idempotency for GET, PUT and DELETE by their semantics, but POST creates something new each time by design. If a POST needs to be safe to repeat — and any POST that moves money does — you have to make it so. The key, the storage, and the replay are that work.

Store the key with a reasonable expiry, scope it to the operation, and return the original response verbatim on a replay. Then a dropped connection is an inconvenience instead of a second invoice.
